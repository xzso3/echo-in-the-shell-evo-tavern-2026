# 并行开发与集成安排

目标：缩短关键路径，同时保证本体能消费工具包产物。依赖 [任务卡](TASKS.md) 与 [本体差距计划](NATIVE_GAP_PLAN.md)。

本轮仅执行S1～S4。原A/B全量矩阵、专门测试开发、独立评审波次和人工交接等待均取消为交付前置；功能范围保持。

## 1. 主控＋独立 task thread 模式

参考用户指定的 [接续会话并主控推进](codex://threads/01a0ca99-e997-7733-9a45-d4ee7b146ff8)，采用独立 Codex task thread 调度，禁止使用 subagent／spawn_agent，也不允许执行任务再嵌套子代理。

- 主控任务：只负责需求／状态文档、派发、依赖协调、读取结果、快速核验和用户沟通；代码、Unity操作和Git集成交给执行任务。
- 功能任务：每个工作包有独立task thread、明确工作树、精确基线SHA、文件边界与交付提交；可安全续用已有执行任务。
- `INT-LT` 集成任务：串行执行共享文件集成、Unity场景接线、S1～S4会合检查和交付检出更新；同样是独立task thread。
- 沿用参考模式，最多 **5个同时运行的执行task thread**，INT-LT占其中一个名额，主控不计入执行名额。不是subagent槽位；实际环境或依赖不足时下调，不为填满数量制造任务。
- 所有执行／集成／返修任务统一 `model: "gpt-6-sol"`、`thinking: "xhigh"`、请求级 `service_tier: "priority"`。主控task也须使用priority；本轮未要求更换主控自身模型。
- Unity Editor 同时只归一个登记执行任务；纯代码任务可继续并行。

分波表中的Sol A/B/C是工作流标签，对应独立task thread而非三个常驻子代理。第4／5执行位用于已就绪的独立工作包与INT-LT，不受先前三个实现槽的限制。

### 调度工具与状态

授权启动开发后，主控使用 `list_projects`／`list_threads` 识别项目及可续用任务，使用 `create_thread` 创建独立执行任务，`send_message_to_thread` 派发／返修，`wait_threads` 等待进度，必要时 `read_thread` 读取交付。创建是异步的；先确认真实threadId，再续派。优先带游标有界等待，不频繁拉取全文。

新开发从当时已验证的集成SHA创建工作树，显式核对分支与HEAD，不能误从项目默认分支开工。原参考会话的旧SHA、旧P2任务、截止日期及自动唤醒不沿用。本轮只更新文档；不因此向参考会话发送消息、创建任务或恢复旧工作。

所有任务回报threadId、hostId、工作树、分支、基线／交付SHA、模型、reasoning与priority核验状态。主控台账保留这些信息以便中断后恢复。成果集成后归档／关闭工作树须先确认内容已保留，不自动清理用户修改。

### priority 配置约束

`service_tier: "priority"` 是实际请求配置要求，不是文本指令。当前可见的 `create_thread`／`send_message_to_thread` schema 提供model与thinking，但没有service_tier参数，禁止伪造这个工具字段。

启动前通过受支持的宿主／任务设置确保priority；当前本机用户配置已观察到 `service_tier = "priority"`，但这不证明新任务不会被其他配置覆盖。每个新建／续派任务核对有效设置或可见的请求元数据，记录“已核验”或“待核验”，不能仅凭提示词宣称已启用。发现default／flex或无法设置时报告具体任务和配置缺口，不静默降级。无法观察服务端实际调度时，只说明已核验的请求配置，不保证服务端返回层级。

官方配置说明：`service_tier` 控制新回合偏好；`fast`映射到请求值`priority`。以实际请求priority为目标，UI若显示Fast不构成冲突。见 [OpenAI配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)。本次只是需求更新，不改全局配置，也不谎称已创建的任务已完成配置。

## 3. 真正关键路径

`G0 → KT-01 → KT-02 → KT-05 → NB-01 → NB-02/NB-03 → KT-07/NB-04 → S1～S4最小检查 → 快速交付`。

地图支路 `KT-03 → KT-04 → KT-08` 与核心战斗支路并行，但两者必须在 KT-10 会合。Skill 可提前写框架，必须等待真实菜单与导出能力落地后完成，不以草稿代替验收。

压缩时间优先做法：先用占位美术跑完整纵向切片，再补合规素材与说明；减少装饰和编辑器美化，保留功能实现与S1～S4；跳过专门负例测试和全面兼容回归。不得以赶工删除本体接入或让工具包独立跑通就交付。

## 4. 文件与 Unity 使用锁

主控维护 `STATUS.md` 中的任务／路径租约：任务ID、threadId、hostId、工作树、基线SHA、模型、thinking、service_tier核验状态、允许目录、Unity使用者及状态。租约不是新软件锁系统，只是明确协作记录。

- 原 Native 核心文件每次只允许一个已登记修改者；NB-02 占 HUD／Interaction／Support，NB-03 占 Quest／Narrative，NB-01 占 RunController／Map／Camera。
- KT-02 早于这些 NB 任务完成 Native 战斗外壳适配，避免同改 Player／Combat 与宿主签名。
- Runtime/Foundation 接口只由当前接口负责人修改；其他执行任务提交提案，主控协调版本。
- 场景／Prefab／材质／Tile 资产由各任务在独立目录创建，公共最终资源由集成者保存；跨目录引用必须以已集成 GUID 为准。
- Unity Editor／批处理只占用一个 checkout 一次。代码执行任务可继续工作，但不在 Editor 正在编译时改同一共享基线。
- ProjectSettings、Packages、Build Settings 和已保存 NativeDemo 由INT-LT按主控指令处理；不要让打包任务自行覆盖。

## 5. 集成节奏与接口变化

每个可运行小步提交代码与资源，主控快速核对diff和引用，由INT-LT复用增量编译结果；不要求每个任务附测试代码。核心短流程在会合点运行一次，后续只在相关改动或故障时重跑。成功后发布新的可集成基线。

接口变更必须列出所有消费者及迁移步骤；由主控通知受影响任务，消费者未迁移前不得标为集成完成。冲突优先回到原负责人解决，禁止直接用 ours／theirs 覆盖场景或丢弃人工改动。

本体集成出现阻断问题时，制作侧可继续素材、文档和不依赖失败接口的工作；不能擅自造临时第二套运行 API。返修优先占原任务槽位，避免无限创建新执行任务增加集成成本。

## 6. 进度报告与时间控制

每波结束提供：已通过关口、可操作产物、未实现本体能力、阻断依赖、待人工事项、下一波安排。G0 后基于实际难度给任务工作量区间和关键路径估算，不把执行任务运行时长当成完整人工验收时长。

按用户已授权的速度策略直接交付快速开发版本，无需再次询问是否省略全量测试。功能缩减仍需确认；未执行的检查如实列为未测。
