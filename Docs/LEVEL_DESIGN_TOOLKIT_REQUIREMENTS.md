## 1. 目标与交付闭环

为联合开发者提供一套最小可用的 Unity 关卡设计工具包。开发者在匹配版本的独立 Unity 工程中导入工具包，通过 Codex 输入创意或参考图，利用制作 Skill 和 ImageGen 完成内容制作，现场试玩，经人工验收后，一键导出 `.unitypackage` 交回主项目。

完整流程：

**导入工具包 → 输入创意／参考图 → 制作地图 → 配置敌人与 Boss → 编排战斗 → 自动检查 → 本地试玩 → 人工验收 → 一键导出 → 主项目导入、校验与预览 → 人工选择接入。**

开发者无需取得完整游戏工程。工具包提供独立试玩所需的公共运行组件、标准测试角色、测试场景和示例资源。开发环境需具备可使用 ImageGen 的 Codex；工具包应附带安装说明和环境检查步骤。

## 2. 工具包组成

采用一个总工具包、四个制作模块，统一版本与导出流程。

| 模块 | 首版职责 |
| --- | --- |
| 地图 | Tilemap 素材、Chunk、障碍、通行接口、地图拼装与校验 |
| 普通敌人 | 基于现有行为模板制作美术与数值变体、生成 Prefab、布置实例 |
| Boss | 基于现有 Boss 机制制作美术与数值变体、生成 Prefab |
| 关卡编排 | 玩家出生点、战斗区域、敌人与 Boss 绑定、门、终点、胜败与重试 |

提供一个总入口 Skill，以及地图、普通敌人、Boss、关卡编排四个专项 Skill。总入口负责理解创意、协调制作和验收；既支持制作完整关卡，也支持只制作 Chunk、敌人或 Boss 变体。

后续制作项目专用 Skill 时，可组合使用 `unity:tilemap-palette-create`、`unity:tilemap-ruletile-createfromsegment`、`unity:sprite-editor`、`unity:unity-cli` 和 `skill-creator`。具体组合属于实现选择，不要求每次制作都执行全部工具。Skill 安装后必须能被 Codex 发现，并能定位目标 Unity 工程。

## 3. 地图与 Chunk 标准

### 3.1 地图表示与尺寸

- 使用 Unity Tilemap。地图由多个道路／地形 Chunk Prefab 实例拼装，首版保留独立实例，不烘焙成单个 Tilemap。
- Chunk 为正方形，尺寸 N 为 3～32 的整数；同一张地图允许混用不同尺寸。
- 所有 Chunk 使用统一单格尺寸。候选值为 **1 格 = 1×1 Unity 世界单位**，须结合现有角色碰撞体和移动速度验证通行后冻结。
- Chunk 原点为左下角格子的外边界顶点；Map 按整数 Tile 格坐标摆放，检查占地重叠。
- 地图内只允许平移，不直接旋转或镜像整个 Prefab。不同朝向由制作工具生成变体，并重新校验端口、碰撞与美术朝向。
- 第一版只支持室外。建筑作为不可进入的外观与静态障碍；不包含建筑室内、跨场景入口和多楼层。

### 3.2 通行接口与拼接

- 每条边最多一个连续通行接口；接口沿边按整格定位，可开启或关闭。
- 接口宽度从 1 格到整条边。普通道路默认使用 1 格接口，开放战场可以使用宽接口或整边开放。
- Chunk 内部道路可弯曲、形成 S 型或拓宽成广场，不要求内部可行走空间呈窄路形状。
- 相邻接口按实际世界位置及通行宽度匹配。大 Chunk 的一个宽接口允许由多个小 Chunk 分段共同对接；各连接段必须对齐且不重叠。
- 未对接的开放部分必须有实际阻挡。端口标记本身不产生阻挡，校验需检查边界封闭情况。
- 只连接实际接触且接口匹配的 Chunk。工具不自动补路，也不自动填补不同尺寸之间的空隙；地图制作者放置其他 Chunk 或补齐阻挡。
- 所有开启端口必须在 Chunk 内互相可达。建筑、围墙等可以形成封闭装饰区域，但不能切断端口间通路。
- 无端口 Chunk 可用于纯装饰或阻挡区域。

### 3.3 内容分类

道路连接方式与美术主题分开描述：

| 维度 | 示例 |
| --- | --- |
| 连接类型 | 直路、转角、T 型、十字、尽头、无道路；S 型作为内部路径变体 |
| 内容主题 | 街道、建筑、草坪、广场等 |
| 空间用途 | 连接段、小转角、开放战斗地面、建筑组合等 |

3×3 等小 Chunk 适合简单连接与局部地形；较大 Chunk 承载复杂布局。大片可行走区域通过地表 Tilemap 表达，障碍单独设置；无需先绑定战斗规则才能制作战斗场地。

### 3.4 美术与碰撞

- 基础风格为俯视角像素风。
- 基础地表 Tile 为 **32×32 像素、32 PPU**，在候选单格尺寸下对应 1 格。
- 建筑、树木等允许跨多格；视觉外观、高度与地面碰撞占地分开设置。
- 统一格子尺寸、原点、图层和基础美术规范；具体图层命名与配置在实现前确定。
- 静态障碍使用 Tilemap Collider 2D；动态门状态由 Map 管理。
- 优先复用统一素材，允许 ImageGen 生成符合规范的补充素材。
- ImageGen 负责美术素材；生成图片须经过尺寸整理、切片、比例、透明背景、接缝、遮挡和碰撞检查，才能作为可玩 Tilemap 内容使用。

### 3.5 AI 与人工共同制作

地图制作流程为：**创意／参考图 → 确认布局与端口 → 生成或复用 Tile Palette／RuleTile 素材 → 制作 Chunk → 自动校验 → 试玩 → 人工精修与验收 → 导出。**

AI 生成可试玩初稿，开发者可在 Unity Tile Palette 等编辑工具中手工精修。后续 AI 修改默认保留人工调整，未经明确要求不整块重建 Chunk。具体保护与更新方式属于待设计实现。

## 4. 战斗内容与关卡编排

### 4.1 战斗区域

- 一个关卡可以包含多个战斗区域。
- 在拼装后的地图上由关卡编辑者圈定区域；区域可跨多个 Chunk，一个 Chunk 也可包含多个区域。
- 首版战斗区域互不重叠。
- 敌人、Boss 和门在关卡层绑定到区域，地形 Chunk 可重复用于不同战斗设计。
- 区域编辑的具体几何形式、刷怪标记表现等尚未冻结，不将此前讨论过但暂停确认的矩形／多边形方案视为已确认要求。

首版提供三种战斗模式：

| 模式 | 规则 |
| --- | --- |
| 自由交战 | 敌人预先布置，不封门；玩家可离开、绕过，默认不要求全部击杀 |
| 清敌遭遇战 | 进入后触发，击败指定敌人后完成，可配置封门 |
| Boss 战 | 进入后激活 Boss，以 Boss 的真实完成事件完成遭遇并解锁对应出口，可配置封门 |

持续生存刷怪、多波次和限时挑战不纳入首版。

### 4.2 触发、撤离与重置

- 每个清敌遭遇战或 Boss 战每局只启动一次，完成后不重复生成敌人。
- 不封门时允许撤离；撤离不重置敌人血量、击杀进度或 Boss 阶段。
- 重开整个测试关卡时统一恢复初始状态。

### 4.3 封门

- 清敌遭遇战和 Boss 战均可选择是否封门。
- 选择封门时，必须绑定足以封住全部出入口的门；战斗开始关闭，完成后打开。
- 自动校验检查遗漏出口，以及关门后玩家是否仍有可站立空间。
- 无法完整封闭的大面积开放区域使用不封门模式。
- 门的开闭状态仍由 Map 持有；关卡规则调用 Map，不保存第二份门状态。

### 4.4 普通敌人

- 提供现有行为模板，具体可用模板清单需技术核验。
- 允许更换美术，调整生命、移动速度、伤害、攻击间隔、射程等模板支持的参数，并在关卡中摆放实例。
- 制作与验收需检查碰撞体、攻击范围和预警。
- 全新移动或攻击逻辑作为工具包功能扩展单独开发，再统一分发；不由每份作品携带各自不兼容的运行实现。

### 4.5 Boss

- 首版使用现有 Boss 机制模板。
- 保留 **攻击 → 破壳 → 核心暴露 → 靠近按 E 完成** 的机制。
- 允许更换美术，调整生命、伤害、预警时间、攻击间隔和核心暴露时长等参数。
- 新攻击类型、阶段转换及胜利机制作为后续工具包扩展。

### 4.6 标准角色与关卡完成

- 工具包统一使用主游戏现有角色的基础移动、碰撞与战斗参数，作为道路、躲避空间与难度的共同参照。
- 作者可调整测试出生点；作品包不修改玩家基础能力。
- 每个测试关卡指定必须完成的清敌遭遇战或 Boss 战；全部完成后解锁终点，玩家到达终点即通关。
- 自由交战默认可绕过，不要求清空所有敌人。
- 玩家死亡后可重开整个测试关卡。
- 上述为可替换的独立试玩接线；正式叙事绑定生效时停用测试接线，由主游戏任务与叙事决定推进和完成条件，避免测试终点与正式流程同时控制关卡结束。

### 4.7 与主线任务、剧本和叙事系统的连接

采用 **关卡事件接口 + 主游戏叙事绑定** 的接入方式。关卡负责提供实际发生的事实及可调用动作；主游戏决定这些事实如何推进任务、触发对白、形成叙事记录和影响后续剧情。

内容分为三个层次：

| 层次 | 职责 |
| --- | --- |
| 可复用内容 | Chunk、普通敌人和 Boss 变体描述自身能力与表现，可用于不同故事 |
| 独立关卡 | 组合地图、遭遇战、门、出生点和测试终点，提供事件与动作接口，可独立试玩 |
| 正式叙事绑定 | 在主项目中把关卡接口连接到任务条件、记忆、对白、行为记录及正式完成规则 |

关卡作品不写死正式主线任务编号、同步度变化或结局逻辑，也不需要携带完整游戏剧本。剧情接入沿用现有状态归属：Quest 管理任务状态，Narrative 管理叙事记录，Map 管理门等通行状态，ECA 检查条件并协调调用，不复制业务状态。

以下是接口用途示例，不是已经冻结的首版 API 清单：

| 方向 | 示例 | 正式绑定用途示例 |
| --- | --- | --- |
| 关卡产生事件 | 与档案终端互动 | 展示指定记忆，更新主线目标 |
| 关卡产生事件 | 实际通过检修通道 | 记录绕行行为，影响后续对白 |
| 关卡产生事件 | 指定遭遇战／Boss 真实完成 | 推进任务，开放后续剧情 |
| 关卡产生事件 | 到达出口 | 检查任务条件，决定是否进入下一段 |
| 主游戏调用动作 | 激活指定遭遇战 | 在剧情条件满足后开启战斗 |
| 主游戏调用动作 | 设置指定门的开闭 | 根据主线进度改变通路 |
| 主游戏调用动作 | 启用互动对象、解锁出口 | 控制剧情节点的可用性 |

关键对象应具有稳定标识，例如 `archive_terminal`、`service_passage`、`boss_encounter`。同一关卡放置多次时，还需区分关卡实例，避免一份关卡的事件触发另一份关卡的绑定。

工具包生成随作品交付的关卡接口清单，列出可订阅事件、可调用动作、对应对象及用途说明。作者用这些接口配置独立测试接线，例如占位对白、Boss 完成后解锁测试终点；主项目集成者再配置正式任务与叙事绑定。

纯战斗关卡可以仅提供必要的战斗完成与出口事件；承担主线剧情的关卡，应在制作前约定必要互动点和事件。支持自由创作作品的后续接入，也支持按主线需要定向委托关卡。

首版按实际主线需要确定最小事件、条件和动作集合，可通过 Unity 组件与 Inspector 实现；从现有 `NativeEcaRules` 的具体接线逐步整理，不恢复全玩法 JSON／Schema 工程，也不在本次确认中扩展为完整剧本编辑器。具体接口清单与绑定表现形式待技术设计确认。

## 5. 测试、校验与人工验收

工具包包括测试场景、标准测试角色、示例邻块和相关校验脚本。

| 测试层次 | 要求 |
| --- | --- |
| 单块试玩 | 检查角色行走、转角、阻挡和视觉效果 |
| 邻块拼接 | 放置测试邻块，检查接口、接缝及跨块通行 |
| 地图校验 | 检查尺寸、原点、接口、占地重叠、区块内外可达性、碰撞配置与边界封闭 |
| 战斗校验 | 检查战斗绑定、封门出口与站立空间；试玩触发、完成、撤离和重置行为 |
| 叙事接入校验 | 检查接口标识与对象引用、实例隔离，以及测试接线和正式绑定的切换 |
| 导出校验 | 检查必要组件、资源依赖、命名和版本信息 |

校验失败时显示具体原因，并定位可定位的问题。自动校验通过后，由作者人工试玩、检查视觉与实际行走／战斗体验并确认验收，再执行一键导出。人工验收记录不能替代接收端检查。

## 6. 包格式、资源隔离与接收流程

### 6.1 制作工具包

以 `.unitypackage` 交付，包含 Skill、标准与模板、公共运行组件、示例素材、测试场景、校验脚本和一键导出工具。导入匹配版本的独立工程后即可开展制作与试玩，无需完整主游戏工程。

### 6.2 作品包

支持两种导出粒度，均使用 `.unitypackage`：

- **单项资源包**：Chunk、普通敌人或 Boss 变体及必要资源依赖。
- **完整关卡包**：地图布局、战斗区域、敌人配置、门、终点、关卡接口清单、作品自身的独立测试接线及必要资源依赖；在安装匹配工具包的工程内可独立试玩。正式主线与叙事绑定由主项目配置。

作品采用“作者标识／作品标识”独立资源目录，减少同名资源和 GUID 冲突。导出只包含作品、必要素材依赖及作品信息，不重复携带公共工具脚本、公共测试场景或标准测试角色。完整关卡自身的内容属于作品，可随完整关卡包交付；公共基础素材与运行脚本由统一工具包提供，导出检查其依赖。

首版通过文件人工交换，不包含在线协作、云端素材库或自动合并。

### 6.3 主项目接收

**导入作品包 → 校验 → 测试场景预览／试玩 → 用户明确选择加入主地图或主关卡。**

导入本身不自动修改现有地图，不自动替换已使用的 Chunk。接收端使用同一套校验规则。

完整关卡经人工选择接入后，集成者根据接口清单配置正式任务与叙事绑定，停用独立测试接线，再验证正式流程。导入和预览本身不自动推进主线或提交叙事记录。

## 7. 版本约束

- Unity：**2021.3.27f1c2**。
- URP：**12.1.12**。
- 每份作品记录所用工具包版本；导入时检查版本兼容性，不匹配时明确提示，避免直接接入主游戏。
- 工具包升级不自动批量修改已有作品，兼容性需单独验证。
- Codex Skill 的安装路径、发现方式和环境检查流程在实现阶段确定并验证。

## 8. 随包示例与最终验收

提供一个小型完整示例关卡，包含：

- 混合尺寸 Chunk 与宽接口拼接。
- 开放战斗地面。
- 自由交战、封门清敌和 Boss 战。
- 必需战斗完成后解锁终点。
- 死亡、重开与通关流程。

示例完整演示制作、试玩和导出流程。最终验收须在干净的匹配版本 Unity 工程中导入工具包，再导入导出的示例关卡，验证资源完整、可试玩、可通关和可重开。

联合开发闭环验收还需证明：另一位开发者仅凭工具包和 Codex 完成新内容、当场试玩并导出；主项目导入后校验通过，资源完整、道路对齐、碰撞正确，能够经人工选择接入游戏。

叙事接入验收需证明：同一关卡可先用测试接线独立运行，再通过正式绑定以真实关卡事件推进主游戏任务或叙事，并由主游戏条件调用关卡动作。切换后测试接线不再重复结算或提前通关；同一关卡的多个实例不会相互误触发。具体演示接口随首版接口清单确定。

验收应记录实际命令、结果与未测范围；静态检查或 Editor 编译不能替代 Play Mode、视觉和人工试玩，也不能据此宣称 Windows 玩家构建已经通过。

## 11. 被后续讨论替代的规则

为避免执行时误用早期结论，以下仅作为变更记录：

| 早期提议 | 最终确认 |
| --- | --- |
| 仅地图制作工具包 | 升级为地图、普通敌人、Boss、关卡编排四模块工具包 |
| 固定 32×32 Chunk | 同图混用 3×3～32×32 正方形 Chunk |
| 固定 Chunk 网格摆放 | 按整数 Tile 格坐标摆放并检查占地 |
| 每边中央端口 | 每边最多一个连续接口，沿边按整格定位 |
| 固定 1 格端口 | 1 格至整边的可变宽接口，道路默认 1 格 |
| 接口仅一对一完整匹配 | 大接口可由多个小接口分段对接，未对接部分封闭 |
| 战斗标记作为 Chunk 局部信息组合 | 战斗区域在关卡层定义和绑定，可跨 Chunk，首版互不重叠 |

建筑室内、多楼层、在线协作、自动合并、持续生存刷怪、多波次、限时挑战，以及新的敌人／Boss 行为机制，均不属于首版交付范围。
