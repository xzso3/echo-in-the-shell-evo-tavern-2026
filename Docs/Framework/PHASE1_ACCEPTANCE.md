# 第一阶段验收用例与报告契约

更新日期：2026-09-22。版本：0.1。当前状态：以下全部为待实现、待执行的验收要求，无新框架运行通过记录。

依据：[实现规范](PHASE1_IMPLEMENTATION_SPEC.md)、[能力清单](PHASE1_CAPABILITIES.md)。任务映射见 [开发任务](PHASE1_TASKS.md)。

## 1. 验证层次

1. 静态：Schema、引用、依赖、能力上下文和资源清单。
2. 纯逻辑：同一 Core/Gameplay 源码在无 Unity 图形环境下执行，使用可控时间与标准输入命令。
3. Unity：编译、导入、样例场景、资源和视觉表现。
4. 内容生产：框架冻结后由第二份内容包证明能力复用。

纯逻辑通过不能代替 Unity 表现验收。历史原型的通过记录不能填写到本表。框架开发过程允许先完成某层，阶段最终验收必须覆盖全部必需层。

## 3. 用例数据格式

使用 JSON 声明用例，P1-01 冻结 Schema，P1-03 实现运行器。必需字段：

| 字段 | 内容 |
| --- | --- |
| case_id / requirement_ids | 稳定用例 ID 及追溯要求 |
| package / entrypoint | 精确版本内容包及测试入口 |
| seed / timestep / max_ticks | 可复现输入、逻辑步和明确超时 |
| setup | 初始测试夹具；与运行中的玩家操作分开 |
| steps | 输入意图、推进时间、等待领域事件等有界操作 |
| expect | 终态、事件次数/顺序、失败代码和资源清理断言 |
| verification_layer | 静态、纯逻辑、Unity 或人工试玩 |

集成路线可以使用“移动到命名标记”的测试驱动，但驱动只能产生标准移动输入，必须经过实际阻挡与路径约束。禁止直接改玩家位置、生命、目标完成状态或门状态来替代路线验收。单元夹具可以构造初始状态，必须明确标识为单元测试。

基础验收用例由契约/验收任务维护，内容 agent 可提交额外用例。第二包的两个终端均为必需目标；不能通过删除目标或放宽断言使关卡通过。

## 4. 工具与报告

需提供四类可重复执行的入口：能力目录导出、内容包静态校验、声明式逻辑用例运行、Unity 导入与场景验证。P1-03/P1-07 交付实际命令及环境说明；本文件中的入口描述不是当前可运行命令。

机器报告至少包含：报告格式版本、内容摘要、依赖摘要、框架版本/摘要、能力目录及 Schema 摘要、运行器版本、执行环境、种子、用例 ID、状态、耗时、期望/实际结果、诊断和产物路径。静态错误包含文件、内容/规则 ID、字段路径、错误代码与原因。

状态使用 `passed`、`failed`、`not_run`、`blocked`。未执行、环境不可用和工具崩溃不能写成 passed。人工视觉检查单独记录检查人、场景、分辨率、观察结果及截图/视频路径；截图本身不代表玩法验收通过。

报告由工具或实际执行记录生成。报告目录不参加源内容摘要；输入变化后重跑受影响检查，框架或能力契约变化时重新建立冻结基线。相同代码在不同运行环境下的结果分别记录，不承诺不同平台的浮点轨迹逐位一致。
