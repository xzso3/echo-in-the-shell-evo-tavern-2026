## 3. 工具使用与持续调度

先发现实际可用的任务工具并调用 `list_projects`，按上述目录核对项目 ID、主机和 `isGitRepository`。不要猜 projectId、threadId 或工具参数。工具缺失时说明具体能力缺口，不能谎称已创建任务或改用未授权方式模拟任务。

通过 `create_thread` 创建任务时提供完整任务书及清晰标题，未获用户指定时不覆盖模型和推理设置。创建是异步的：

1. 立即记录创建请求及返回的 ID。返回 `clientThreadId` 时标记为 `creating`，不能把它当 `threadId` 传给等待或消息工具。
2. 通过工具支持的状态查询或 `list_threads` 获取真实 `threadId`、主机和工作区；只匹配能够明确对应本次派发的任务。创建结果不明确时先核实，不直接重试创建。
3. 报告实际创建的任务时使用工具返回的原始标题，并按应用要求输出创建任务链接或指令。
4. 使用 `wait_threads` 等待已确认的任务，每次最多等待约 30—60 秒，保存并复用各任务的 cursor；将当前运行任务放在一个等待调用中。
5. 只有出现交付、失败、需要补充输入或状态歧义时，才用 `read_thread` 读取必要详情。避免反复读取整个对话。
6. 通过 `send_message_to_thread` 补充信息、返修或续派已有工作包。不要反复发送“继续”或在上一轮仍进行时重复派发同一工作。

工具参数以本次实际可用工具为准；工作区机制可参阅 [官方 worktree 文档](https://learn.chatgpt.com/docs/environments/git-worktrees)。文件隔离不能替代依赖管理和合并后的验证。

只要仍有可执行工作或正在运行的任务，就继续调度和等待，不因“已派发”“正在执行”而结束主控工作。约每分钟提供简短进度，说明完成的交付、当前运行项和下一项依赖；没有变化时不要反复催促执行任务。

不要承诺当前会话结束、应用退出或额度耗尽后仍会自动运行。发生中断时依靠台账恢复；本任务不要求额外创建定时自动化。

## 8. 审查、合并和返修闭环

每个交付按以下顺序处理：

1. 主控核对任务书、提交、路径范围和报告是否齐全。缺少证据则发回原任务补齐，状态保持 `needs_revision`。
2. 将具体交付提交和基线交给 INT-00。它审查实现是否符合契约、测试是否验证要求、是否越界或削弱断言，在自己的工作区使用独立的临时候选分支合入并执行受影响检查。`codex/p1-integration` 保持在最后通过的版本，候选通过后才推进它；保留失败诊断和有价值的修改，不用破坏性重置清理问题。
3. INT-00 返回原基线、候选集成提交、检查结果和可消费的新基线。只有通过后，主控更新 `accepted_base_commit`，将对应交付标记为 `accepted`，放行下游。
4. 合并失败或检查失败时，候选版本不得作为下游起点。INT-00 保护最后通过的基线；需要修复时由主控继续原模块任务，或创建范围明确的新修复任务。冲突处理和代码修复均不由主控亲自完成。
5. 不把多个分支各自通过的结果拼成“合并后通过”。集成任务必须对实际合并后的源码执行受影响检查；P1-09/P1-11 负责完整关口。

INT-00 持续负责 Git 集成和日常验证，P1-09 负责正式 G1/G2 与冻结证据，P1-11 是单独创建的最终验收任务。它们职责互补，不因已有集成任务就省略 09 或 11。

- 等待 cursor、最后有效进展、报告和证据路径、阻塞原因及下一步。
- Unity 占用任务、冻结清单及 A/B 内容摘要、G1/G2/G3 状态。

任务状态采用 `pending → ready → creating → running → submitted → integrating → accepted`；返修用 `needs_revision`，等待外部条件用 `blocked`，放弃的尝试保留为 `superseded`。这里是项目台账状态，不代表应用或 goal 工具的同名状态。

恢复时先读台账，再用任务和 Git 工具核对实际状态。已运行的任务继续等待；已交付但未合入的任务继续审查；没有得到明确创建结果的任务先查询；有有效验收证据的任务不重复开发。台账与实际不符时以可核实证据修正，并留下原因。

## 10. 完成标准与停止条件

只有全部满足以下条件，才向用户报告第一阶段完成：

- P1-01 至 P1-11 全部有已接受的交付，必要修复已经合入。
- G1、G2、G3 全部通过；A01—A26 的所有相关必需子例和必需验证层有真实记录，没有必需项处于 failed、not_run 或 blocked。
- 样例 A、B 的交战和绕行路线实际通过；移动、战斗和交互经过正式输入与领域逻辑，没有传送或强设完成状态代替验证。
- B 在冻结框架上仅通过内容与资源实现两个必需终端等变化。若 B 暴露能力不足，先由框架任务修复、重新验证 A 并冻结，再重新执行 B 的验证。
- Unity 编译、导入、输入、表现和要求的分辨率检查完成；历史原型检查及无图形测试不能代替新框架的 Unity 验证。
- 所有交付位于明确的最终集成版本，存在可复现运行说明、两份源内容包、工具入口、真实报告、视觉证据和后续能力缺口清单。
- 没有仍在修改交付范围的任务或未处理的阻塞。无需为了结束本阶段而删除或归档工作区。

执行期间用户补充信息时，将其纳入当前计划；用户仅询问状态时简要回答后继续。用户要求暂停时停止新派发，告知运行任务在安全检查点保存状态，并核实它们是否真的停下；不能只改台账就宣称全部暂停。

如果遇到权限、额度、必需工具、Unity 环境或必须由用户裁决的产品冲突，先完成不受影响的工作，再报告具体阻塞、已经尝试的解决办法、保存的进度和用户所需的最小操作。不要向执行任务代替用户批准权限，也不要用减少验收要求绕开阻塞。因平台中断而停止时明确说明尚未完成及恢复入口。

最终只报告：完成范围、最终分支与提交、G1/G2/G3 及必需验收结论、运行入口、证据位置和已知限制。未达完成标准时报告“未完成”和准确原因，不把已创建或已结束的任务数量当成完成证明。

现在开始：核对项目与已有进度，建立或复用台账，按需派发 P1-00 和 INT-00，然后按依赖持续调度 P1-01 至 P1-11。
