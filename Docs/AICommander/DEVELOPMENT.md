# AI 指挥官与战术平板开发规范

状态：开发规范；本阶段已启动，实时派发与集成进度见[状态台账](STATUS.md)。产品依据为 [阶段需求](PHASE_TASKS.md)，调度见 [执行计划](EXECUTION.md)。

## 1. 最新执行约束

用户要求极致速度：**不编写或运行自动化测试，不设中间验收关口，只保留交付前人工校验。** 不建立探针、夹具、覆盖率、回归矩阵或截图批处理。Unity 为形成可运行交付而发生的正常导入／编译属于开发过程；遇到编译错误直接修复，不另起测试轮次。

已确认的请求合法性检查、重复执行保护、隐藏内容过滤、Key不落盘等是产品逻辑，仍须实现，不能因取消测试而删除。本文件中的接口名、目录、阈值与字段为工程默认建议；允许执行任务做不改变产品行为的简化，不要求每个技术细节再确认。

## 2. 最短交付路径

在现有Native主线接入：启动配置界面 → C#直连请求 → 安全节点状态快照 → 对白／提案 → 现有支援合同 → 真正效果反馈。手机替换成已认可的战术平板，并统一处理暂停。

不做演示脚本、不重写战斗／任务系统，不再开发独立代理服务器，不引入通用Agent框架。优先沿用UnityWebRequest和项目已具备的JSON能力；SDK不是必交付项。先让功能组件接通，再替换最终美术，不等待设计资源才写业务代码。

## 5. 请求与响应契约

### 5.1 配置与HTTP

首页标签写清“API Base URL（例如以 /v1 结尾）”。归一化时移除尾斜杠；已提供完整`/chat/completions`则直接使用；以`/v1`结尾则追加`/chat/completions`；仅主机地址则追加`/v1/chat/completions`。其他路径视为用户显式前缀，只追加`/chat/completions`，页面展示最终请求地址，避免重复`/v1`。不自动猜测供应商专有协议。

请求为POST，JSON Content-Type，Bearer Key；`model`使用原样配置的模型ID，`stream:false`，`messages`承载指令、状态与对话。不传tools，不依赖provider特有的reasoning、temperature或JSON Schema参数。若现场服务支持额外参数，也不为本轮新增配置面板。

首页测试连接用同一端点发送一个最短普通文本请求，只验证返回有效文本，不要求返回游戏提案结构、不调用models列表。配置修改后取消旧连接检查，显示状态为待检查；测试失败可重试或离线开始，不能永久锁住开始入口。

Key只驻内存，不用PlayerPrefs／ScriptableObject／StreamingAssets存储；可保存地址和模型。超时默认15秒且可配置，使用真实时间。不记录Authorization、Key或完整请求体；错误提示用状态类别，服务返回原文需移除可能含凭据的内容后才显示。

### 5.2 上下文装配

一次请求依次放：固定指挥官规则、最新可公开快照、最近6轮成功对话及相关游戏反馈、当前玩家消息。快照仅含白名单字段，不序列化整个Run对象或全文游戏设计文档。

建议快照字段：`player_health`、`current_objective`、`known_memories`、`known_routes`、`boss_stage`、`available_support_options`、`recent_facts`。公开文本长度应有限，避免一次附带全部日志；初始每条输入上限1000字符、回复上限1200字符可作为实现默认。不要为上下文压缩再调用模型。

支援合法选项由Unity产生不透明`option_id`，映射具体kind/memory/tier及目标；模型只返回该ID。游戏端显示的收益和代价完全从现有配置读取，不相信模型对白中的数值承诺。未发现路线／记忆在快照生成阶段就剔除，不能仅在prompt里嘱咐不泄露。

聊天UI保留本局消息；发给LLM仅取最近6轮成功对话。失败、取消不占成功历史；相关支援结果作为游戏事实附在原提案轮次或当前近期事实中，避免重复插入。旧聊天中的提案状态可以更新，但不把模型历史输出当权威游戏事实。

### 5.3 有限结构化回复

推荐最低协议：

```json
{
  "reply": "指挥官的简短回应。",
  "proposal": { "kind": "medical", "option_id": "本次快照提供的合法ID" }
}
```

无提案时`proposal:null`；kind只允许`medical`、`weakpoint`。Unity负责生成proposalId、runId、requestId，模型不得指定这些身份。解析外层`choices[0].message.content`再解析内层JSON；可移除单一包裹的markdown代码围栏，不从任意散文中猜测和执行动作。不依赖LLM原生tool call。

空内容、截断内容、非法JSON、未知kind、未知option_id、kind与option不一致均作为本次请求失败，不执行提案；保留玩家输入以手动重试，不自动发修复请求。回复正文按纯文本渲染，关闭TMP富文本或转义标记，不让模型注入布局标签。

固定指令说明角色语气、仅依据已知事实、不替玩家授权、只能推荐合法选项、缺少方案时解释原因、只能输出约定JSON。不要要求模型长篇推理或输出隐含思考过程。

## 6. 请求、聊天与重开生命周期

Session状态为`Idle / Requesting`；结果是完成、失败或取消，不建复杂恢复状态机。

发送时捕获当前本局身份、焦点实例／目标上下文和递增请求代次。同一时间仅一个请求，发送立即禁用。成功回调必须仍匹配当前请求、本局身份和允许的上下文；关闭手机、重开、离开有效Run、配置变化时失效并取消。迟到结果直接丢弃，不追加聊天／合同。

切换手机页签只是阅读操作，不取消请求；回到通讯页可见结果。退出输入焦点与取消HTTP必须拆成不同方法，不能复用现有CancelComposition造成切页丢请求。手机彻底关闭才取消；草稿保留，重开才清除本局草稿。

等待期间可取消、滚动和看记录；UI不因HTTP等待阻塞主线程。输入可保持但不能重复发送。失败时展示简短原因、保留原问题，玩家明确重试。关闭手机之后不自动重新发送。

重开顺序：失效旧Session代次 → 取消请求 → 取消未完成合同／提案 → 释放手机暂停状态 → 重载／创建新局。程序级设置对象保留Key，新局Session重新建立；不继承旧局消息或任何待执行动作。

## 7. 提案与合同的执行规则

提案状态建议`Available → Viewing → Executed / Rejected / Cancelled / Expired / Failed`；只有非终态可进入确认。仅允许一张待确认合同，手动与AI支援复用同一Support入口，不能互相静默覆盖。

模型响应只产生Available卡片，不立即调用Support.Request，以免后台回复占用合同槽。点击查看时重查选项、合法记忆、当前焦点Boss／玩家、Run与未使用条件，再请求现有合同。另一合同未处理时先提示处理，不替玩家拒绝。

接受时再次核对请求来源与目标，调用Support.Confirm，由其完成效果、使用状态和授权事件。桥接层不重复调用Narrative.RecordSupport。同步后的实际结果进入聊天：从正式结果／前后真实值生成，不照抄AI承诺。

拒绝或关闭合同调用取消并终结本提案；关闭整个手机时若合同覆盖窗正打开，也按关闭合同处理。已完成支援永不回滚。其他尚未打开的提案卡保留，下次查看重新校验。

网络不是支援执行前提。人工支援仍可从支援页发起，使用相同合同样式和权威执行器；AI失败不锁住手动入口。状态变化无法执行时仅显示失败／过期，无代价。

## 8. 暂停设计：保持业务活跃、停止战斗推进

当前`Running`被生命、支援、输入、Boss和关卡宿主共同使用。直接把它改为false会造成清理预警、支援拒绝或实例停用，因此**暂停不等于Run结束**。

最快方案可使用统一手机暂停拥有者保存原Time.timeScale并置零，同时显式屏蔽世界输入和仍在Update里执行的战斗逻辑。不要仅认为timeScale=0已足够：Time.time到点的攻击、Update伤害判断、按键以及手动步进仍可能执行一次。为实际需要的更新入口添加可推进检查，但生命／支援／合法交互的存活条件仍可为真。

统一语义建议：`IsRunActive`描述进行中的活玩家，`IsCombatAdvancing = IsRunActive && !PhonePaused`用于移动／攻击／伤害／世界互动。不必全局重命名现有Running；以兼容属性和局部守卫最小接入。

缩放时间冻结移动、物理、弹丸、攻击冷却、核心窗口、Buff、关卡计时。UI动画、光标、滚动、网络超时用未缩放时间。不要为暂停禁用战斗GameObject或改变焦点：已有OnDisable可能清场或重置Boss阶段。

所有手机入口统一走Open/Close，包括快捷键、按钮、最终节点选择和结局接续。手机开时阻断WASD、Space、E、装备／Buff快捷键；Esc先关闭合同，再关闭平板，关闭合同取消提案；Tab关闭平板时不能透传成游戏操作。原开火模式不变，不留下持续移动输入。

从最终选择切入结局时，完成逻辑可在手机暂停中执行；在演出开始前释放手机暂停，否则现有缩放时间协程会卡住。结局后的手机不恢复战斗，Close只释放自身持有的暂停原因。重开／返回首页正常恢复时钟，不盲目把其他系统持有的暂停取消。

安全节点用当前实际玩家位置和有效Run判断，移除敌近排斥。暂停期间仍视为合法安全通讯；非安全节点只禁自由输入，不禁阅读／手动支援。

## 9. UI与美术落地

基准方向见 [认可草图](References/tactical-tablet-concept.png)，不重新做品牌探索。设计负责人读取imagegen、interface-design、Unity UI相关Skill，以内置ImageGen生成项目资产。原草图不直接作为整张可交互界面背景。

建议布局基准1280×720，平板约占屏宽85%，保留游戏背景边缘；按屏幕等比适配，不把参考图每个像素当硬性坐标。外壳采用不拉坏转角的切片／固定角装配，屏幕内采用原生布局与独立滚动。保留Point采样的像素边缘，不对所有UI素材机械套用地表32PPU规则。

必要资产优先级：平板外壳／边角、实体返回键、指挥官信号头像、三个标签图标、授权提示图标。状态变化可用Unity色彩与边框表达，不为每个hover再生成大图。最终贴图存项目内，记录来源prompt，保留透明背景。

必要视图：

| 视图 | 组件与行为 |
| --- | --- |
| 首页配置 | URL、Key掩码、model、超时、测试连接及其等待／结果、开始、离线进入 |
| 通讯 | 指挥官身份、消息列表、AI/本地来源区分、提案卡、输入、发送／取消、非安全区说明 |
| 合同覆盖窗 | Unity生成的效果／记忆／授权／代价、接受、拒绝和关闭，背景聊天位置保持 |
| 支援 | 现有医疗与弱点解析、合法记忆／档位、手动查看合同，不新增机制 |
| 记录 | 已有记忆、行为和本局结果；保留必要的保留异议／回声改写入口及原剧情操作 |
| 最终选择／结局手机 | 保留原写入／销毁、重开和结局接续；不能被UI改版删掉 |

底部三入口“通讯／支援／记录”；在线状态只表示AI通讯，不宣称全服上线。中文为真实TMP文字，复用现有字体并覆盖按钮和新增文案；动态回复须有中文fallback，避免生成字形缺失。不得把Key显示在截图、错误窗或连接状态标签中。

UI-03可以先用原生色块搭结构，UI-02同时产图，最后替换Image/Sprite。Unity场景保存只由INT-AI进行；设计者先交独立资源和Prefab／装配代码，避免抢占正在使用的Editor。

## 10. 最终交付条件

交付所有功能代码、最终资源、配置入口、已接线场景及简短使用说明。当前可玩入口由INT-AI与主控确认，不擅自把实验场景替换为唯一构建场景。

没有自动测试或中间功能验收要求。最终人工校验按 [执行计划](EXECUTION.md) 一次完成，发现启动、聊天、支援、暂停或UI阻断才返修相关路径。完整主线／多分辨率／异常组合等未做即注明，不补跑全套。
