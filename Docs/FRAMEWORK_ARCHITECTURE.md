# 模块化框架与 ECA 架构决策记录

更新日期：2026-09-22。

状态：架构方向与第一阶段目标已确认，尚未开始框架实现。本文件记录已确认决策与待定问题。第一阶段的工程基线见 [实现规范](Framework/PHASE1_IMPLEMENTATION_SPEC.md)，配套能力、验收和任务文档由该入口关联。

[核心游戏设计文档](ECHO_IN_THE_SHELL_GAME_DESIGN.md)定义目标体验；本文件补充面向 AI 内容生产的工程架构。现有代码、场景和历史验证记录仍描述战斗演示原型，不能作为新框架已经完成的证明。

## 1. 已确认：建设目标与模块范围

重构游戏代码，先建立适合当前需求的轻量 framework，为后续 AI 内容生产 pipeline 提供稳定的模块接口、内容规范、校验与运行能力。现有实现作为玩法参考和可评估的复用来源。

目标模块包括但不限于：

- ECA（Event–Condition–Action）规则系统。
- 独立的区块地图系统，每个 Chunk 由 N×N 个 Tile 构成；具体 N 与地图数据模型待讨论。
- 敌方角色系统，包含 Sprite、动画、攻击方式、特效等。
- 标准战斗关卡脚本系统，支持专门的关卡设计 agent 生产内容。
- 剧情系统、NPC 系统、道具系统。

各系统逐项讨论职责、数据、接口和验证方式，再确定具体实现范围。

## 2. 已确认：内容生产与代码开发分工

| 角色 | 职责 |
| --- | --- |
| 内容 agent | 主要生成符合规范的配置与资源，组合已有能力并引用已有内容 |
| 框架开发 agent | 实现新增代码能力，维护运行代码、配置规范、示例及验证能力 |

能力需要明确的标识、参数与行为契约，供内容生产和校验使用。内容 agent 需要的机制超出已有能力时，由框架开发流程扩展能力后再接入内容。

## 3. 已确认：ECA 的覆盖范围与定位

ECA 是玩法逻辑的中间表示（IR），承担统一的规则编排。覆盖基础关卡、任务和剧情，并深入敌人行为、攻击阶段、Buff、NPC 交互及道具效果。

- Event 表达事件及其上下文。
- Condition 判断规则是否适用。
- Action 调用具体模块提供的能力。

移动、寻路、弹丸运动等持续能力由专门模块执行；ECA 通过明确接口组织和控制它们。地图布局、角色资源、攻击参数和道具静态属性保留各自的数据规范，ECA 通过标识引用这些内容。

首版由内容 agent 直接生成 JSON 格式的 ECA IR。后续若引入面向特定领域的上层描述，可转换为同一套 IR。具体字段和版本兼容协议尚待确定，已确认的格式与生产契约见第 9 节。

## 4. 已确认：toolkit 形态

首版使用结构化配置，不制作 ECA 编辑器；当前整体 toolkit 也不以编辑器产品为建设方向。

工具链围绕内容规范、校验、资源引用解析、运行时加载和执行组织。调试与验证采用结构化日志、执行轨迹和验证报告；不将节点编辑器或可视化调试面板作为首版前提。

## 5. 已确认：事件定义与监听范围

事件具有明确类型、来源、关联对象和载荷；规则绑定时明确监听范围。例如“自身死亡”“当前遭遇内敌人死亡”和“本局任务完成”使用不同作用域。

| 事件类别 | 定义方式 |
| --- | --- |
| 框架基础事件 | 战斗、实体生命周期等由框架统一定义 |
| 内容自定义事件 | 内容 agent 可以在配置中声明剧情和关卡事件 |

两类事件都需要明确的数据类型，并通过类型校验。同一份角色规则绑定到多个实例时，应按作用域匹配各实例关联的事件。

事件标识规范、载荷类型集合、发送权限、具体排序、调度预算及事件去重策略尚待细化。已确认的队列与同步结算边界见第 8 节。

## 6. 已确认：Condition 与状态模型

Condition 只读取和判断，不消耗物品、修改变量或触发其他规则。使用 `all`、`any`、`not` 对已注册的判断能力进行结构化组合。

条件的数据来源包括事件载荷、执行上下文、模块公开状态及配置声明的自定义变量。

内容 agent 可以声明自定义状态变量，覆盖剧情、关卡、角色和技能等局部状态。每个变量必须声明类型、默认值和作用域；变量修改通过明确的 Action 完成。

| 示例变量 | 示例类型 | 作用域示例 |
| --- | --- | --- |
| 是否保留异常记忆 | 布尔 | 本局 |
| 已激活节点数量 | 整数 | 当前关卡 |
| NPC 当前交互阶段 | 枚举 | NPC 实例 |
| 技能当前连击次数 | 整数 | 技能执行实例 |

这些示例表达已确认的能力范围，具体字段名称、支持的类型集合与作用域协议仍需在 IR 规范中细化。

生命值、背包、任务正式完成状态等由对应模块管理的数据，通过模块接口查询和修改。自定义变量不能成为这些模块状态的另一套权威来源。

## 7. 已确认：Action 执行与重复触发

Action 区分即时动作和持续动作，使用统一的执行结果表达运行中、成功、失败或取消。即时动作在本次调用中完成；持续动作需要运行框架跟踪其完成状态。

首版提供以下组合能力：

| 组合 | 语义 |
| --- | --- |
| 顺序 | 前一个动作成功后执行下一个 |
| 并行 | 同时启动多个动作，默认等待全部成功 |
| 等待 | 等待指定时间或指定事件；事件等待可设置超时 |
| 有限重复 | 按配置次数执行一组动作 |

具体运动、伤害计算等仍由各模块执行，ECA 负责组织调用与衔接结果。

执行实例归属明确的生命周期作用域。作用域结束时取消未完成动作、解除事件监听并清理临时资源。默认失败行为是停止当前流程并报告失败；取消不会自动撤销已经造成的伤害或其他已提交效果。支援交易等需要整体一致性的操作由专门模块保证。

一条规则尚未执行完时再次收到有效触发，按该规则的重复触发策略处理：

| 策略 | 行为 |
| --- | --- |
| 忽略（默认） | 当前执行继续，不启动新实例 |
| 重启 | 取消旧执行，从头开始 |
| 排队 | 当前完成后处理下一次 |
| 并发 | 创建独立执行实例 |

排队与并发必须配置上限。容量耗尽时的行为、排队执行前的条件复查、重启清理顺序、并行动作失败时的收束细节及取消完成协议尚待细化。

## 8. 已确认：事件调度与同步结算钩子

普通事件与同步结算钩子使用明确区分的执行入口：

| 入口 | 用途 | 执行方式 |
| --- | --- | --- |
| 普通事件 | 进入区域、角色死亡、任务完成、剧情信号等已发生的事实 | 入队，在明确的逻辑调度点处理 |
| 同步结算钩子 | 伤害减免、致死保护、交互准入等需要在结果提交前作出的判断 | 在模块指定的结算阶段立即执行，返回后继续结算 |

普通动作产生的新事件继续入队，不通过规则间的同步递归调用传播。首版采用单线程逻辑调度；并行 Action 表示多个流程同时推进，不表示使用多线程执行玩法逻辑。

同步结算钩子遵循以下边界：

- 框架定义可接入阶段，内容配置绑定已有钩子。
- 只允许该阶段注册的即时操作，例如调整候选伤害或拒绝本次交互。
- 等待、持续动作和跨时间流程通过普通事件启动。
- 所属模块负责提交最终状态，保证生命变化、护盾消耗等关联结果一致。

典型伤害流程为：攻击命中 → 同步结算钩子形成候选结果 → 战斗模块统一提交生命与护盾变化 → 发出伤害结算事件 → ECA 处理受击表现、反击等后续规则。

具体调度阶段、同阶段排序、事件链预算、钩子执行顺序及钩子异常处理仍需在实现规范中确定。

## 9. 已确认：JSON IR、能力目录与校验契约

首版使用 JSON 作为 ECA IR 格式，配套两层静态校验：

- 结构校验：通过 JSON Schema 检查字段、类型、必填参数及配置结构。
- 语义校验：检查能力存在性、资源引用、变量作用域，以及动作是否允许用于指定钩子等跨字段和领域约束。

框架导出机器可读的能力目录，供内容 agent 查询：

| 能力类别 | 描述内容 |
| --- | --- |
| Event | 标识、载荷类型、来源及可监听范围 |
| Condition | 标识、参数、可读取的上下文 |
| Action | 标识、参数、执行结果、即时或持续、取消行为 |
| Hook | 所属模块、结算阶段、允许的操作 |
| 内容引用 | 可引用的角色、地图、动画、特效、道具等类型 |

能力目录从框架的实际注册信息导出，参数定义同时用于生成校验规范，避免目录、规范和运行实现分别维护后产生偏差。

内容 agent 读取能力目录、配置规范与资源清单，生成配置后执行结构及语义校验，根据定位信息修正错误，再进入运行验证。校验错误需包含文件、规则 ID、字段位置与原因。

配置声明格式版本和所需能力版本，用于判断框架升级后的兼容性。静态校验发现配置问题，实际行为仍通过运行验证确认。版本字段、兼容规则、目录结构及报告编码尚待细化。

## 10. 已确认：运行实例与逻辑生命周期

运行模型区分共享定义、规则集实例与单次执行实例：

| 对象 | 职责 |
| --- | --- |
| 规则定义 | 共享的只读配置，可由多个实例复用 |
| 规则集实例 | 将规则绑定到具体对象，保存冷却、触发次数等实例状态 |
| 执行实例 | 一次触发产生的流程，保存本次上下文及执行进度 |

实例与变量归属明确的逻辑作用域：

| 作用域 | 典型内容 | 结束时机 |
| --- | --- | --- |
| 本局 | 跨关剧情、记忆、同步度与差异度 | 本局结束 |
| 关卡／遭遇 | 刷怪流程、区域机关、遭遇计数 | 对应关卡或遭遇结束 |
| 实体 | 角色行为、NPC 局部状态、Buff 规则 | 实体被正式移除 |
| 单次执行 | 技能临时变量、等待、并行子动作 | 本次执行完成或取消 |

逻辑生命周期与 Unity GameObject 解耦。隐藏模型、切换表现或回收显示对象，不自动清除实体逻辑状态。

死亡与移除分开：角色死亡后停止普通战斗行为，但掉落、死亡分裂等规则仍需完成。需要在实体移除后继续的流程，显式交给仍有效的关卡作用域，并携带死亡位置等必要数据。

暂停保留执行进度；作用域结束才取消所属流程、解除监听并释放临时资源。游戏模拟暂停时，通讯、UI 和结局服务可以按独立时钟继续运行，具体时间协议仍需定义。

具体作用域标识、父子及关联关系、跨作用域交接、上下文取值时机、绑定与解绑顺序、状态恢复协议尚待细化。首版保存与恢复范围见第 31 节。

## 11. 已确认：轻量 framework 分层

framework 分为四个部分，JSON 配置与美术资源作为独立内容，通过稳定 ID 加载和引用：

| 部分 | 职责 |
| --- | --- |
| Core：运行核心 | ECA 执行、事件调度、作用域、实例管理、时钟接口、能力注册与执行追踪 |
| Gameplay Modules：玩法模块 | 地图、角色、战斗、道具、关卡、任务、剧情、NPC 各自的数据和规则 |
| Unity Host：Unity 宿主与适配 | 输入、画面、动画、音频、资源加载及 Unity 生命周期接入 |
| Tooling：生产与验证工具 | 能力目录导出、Schema 生成、内容校验、逻辑测试和报告输出 |

Core 使用不依赖 Unity 的 C# 实现。玩法模块管理自身状态，通过明确接口请求空间查询、动画播放等宿主能力；Unity 提供对应实现。

ECA 组织流程，玩法模块执行所属规则，Unity 适配层接入引擎能力。例如 ECA 启动攻击，战斗模块创建攻击实例并负责判定及伤害提交，Unity 展示预警和动画，提交后的事件再交给 ECA 处理。

核心逻辑支持在无 Unity 图形环境下验证，通过可控时间推进检查执行轨迹。动画、资源导入、画面和引擎交互继续通过 Unity 验证。

首版启动时显式组装模块与接口，模块之间通过查询接口、命令和事件协作。新增玩法模块时同步注册它提供的事件、条件、动作和内容类型，并更新导出的能力目录。

具体程序集划分、模块依赖、宿主接口及启动顺序尚待细化。

## 12. 已确认：Tile、Chunk、Map 与 Level

区块地图采用四层内容结构：

| 层级 | 职责 |
| --- | --- |
| TileDefinition | 定义地块类型、外观引用、基础通行属性和地形标签 |
| ChunkDefinition | 定义 N×N Tile 布局、静态摆放和命名标记 |
| MapDefinition | 定义 Chunk 的组合、放置位置与连接关系 |
| LevelDefinition | 引用地图，配置敌人、NPC、遭遇、任务、剧情和 ECA 规则 |

同一张地图统一 N 和 Tile 的世界尺寸，贴图像素尺寸单独配置。N 的具体取值尚未确定。

Chunk 模板可以重复使用，每次放置具有独立实例 ID；模板中的同名标记通过实例 ID 区分。地图提供出生点、入口、交互点、触发区域等空间标记，关卡配置绑定具体实体与玩法规则。

房间、安全区、遭遇区具有独立的区域定义，可以跨越多个 Chunk。角色在连续空间中移动；Tile 与 Chunk 用于组织地图数据，地图模块提供碰撞、通行和寻路查询。

后续区块生产 agent 负责空间内容，关卡设计 agent 负责组合地图与玩法。同一个 Chunk 模板可以在不同关卡中承载不同遭遇或剧情。

Chunk 内部分层与阻挡来源见第 13 节，连接与可达性验证见第 14 节，首版生成、加载与状态保留方案见第 15 节。具体坐标及状态恢复协议尚待细化。

## 13. 已确认：Chunk 数据分层与统一阻挡来源

Chunk 内部区分四类数据：

| 数据 | 内容 | 示例 |
| --- | --- | --- |
| 地形网格 | N×N 格地形，引用 TileDefinition | 道路、地板、水面、实体墙 |
| 地表装饰 | 地面的视觉细节 | 标线、污渍、裂纹、碎纸 |
| 静态物件 | 独立外观、放置位置和阻挡范围，可跨多个 Tile | 建筑、设备柜、固定路障 |
| 空间标记 | 命名位置、区域和连接点 | 出生点、NPC 位置、入口、遭遇区 |

地表装饰默认只影响视觉。静态物件的阻挡范围随物件定义保存，摆放时一起变换；视觉轮廓可以大于实际占地范围。

碰撞、视线与寻路查询以统一的阻挡定义为数据来源，分别描述是否阻挡角色移动、是否阻挡弹丸、是否遮挡视线。地图模块据此构建查询数据，寻路还需考虑角色体积。

门、宝箱、可破坏墙等具有运行状态的对象由实体系统管理，通过地图接口更新动态阻挡。地图提供位置标记，关卡实例化对应实体，所属模块处理状态变更并更新阻挡，ECA 通过动作调用这些能力。

可破坏墙的底层地形与墙实体分别定义，墙被移除后撤销它贡献的阻挡。动态更新后的通行、视线和寻路查询继续使用统一阻挡来源。

内容生产可分别生成地形、装饰、物件与标记，工具据此检查出生点被堵、通道过窄、物件越界等问题。具体几何类型、动态阻挡合成、跨区块物件归属和校验规则尚待细化。

## 14. 已确认：Chunk 连接与可达性验证

Chunk 采用具名连接端口，Map 声明实例端口之间的连接关系，并校验实际几何与可达性。

| 端口字段 | 含义 |
| --- | --- |
| 端口 ID | 如 east_road、north_doorway |
| 所在边界 | 东、西、南、北 |
| 位置与宽度 | 边界上允许通行的区间 |
| 类型或标签 | 道路、走廊、门洞等匹配信息 |

端口可以覆盖整段开放边界，适用于城市街道和广场。Map 通过 Chunk 实例 ID 与端口 ID 指定连接，例如 street_01.east_road 与 plaza_01.west_road。

连接声明表达设计意图，实际通行仍由地图几何决定。验证分为三层：

| 检查 | 内容 |
| --- | --- |
| 配置与位置 | 端口存在性、区块位置与朝向、端口区间匹配 |
| 实际通行 | 接缝是否被地形或物件堵塞，指定体积的角色是否能通过 |
| 关键可达性 | 玩家出生点能否到达关卡要求的目标与出口 |

Chunk 内部入口和出口之间也需检查通行，端口已连接不能替代整条路径验证。关卡可以声明必须验证的路径，例如出生点到任务节点、经避战路线到记忆节点、Boss 区域入口到最终交互位置。

涉及门、机关和剧情解锁的路径需指定验证状态，并通过运行测试检查状态转换。工具也应识别未声明的跨区块通路，以发现意外绕过关卡目标的路线。

地图生产流程可以先规划连接关系，再选择和摆放 Chunk，最后根据验证报告修正布局。端口精确字段、变换规则、状态测试配置与报告格式尚待细化。

## 15. 已确认：首版地图生成、加载与状态保留

首版采用预生成的有限地图、整图逻辑加载和同局状态保留：

| 环节 | 首版方式 |
| --- | --- |
| 内容生产 | agent 提前生成 Chunk 与 Map 配置，通过校验后交付 |
| 地图装配 | 运行时按 MapDefinition 中的确定布局实例化 |
| 地图加载 | 以有限地图为单位加载完整逻辑数据 |
| 显示管理 | Unity 宿主管理显示与裁剪 |
| 状态保留 | 同一局内保留地图中已经发生的变化 |

Chunk 用于内容复用、拼装与定位。后续需要更大地图时，可在同一数据协议上增加分区加载。

配置定义与地图实例状态分开。例如门的配置是初始关闭，玩家开门后的实例状态则是已打开。同局跨区块或离开镜头不会重置状态，重访时保留门和可破坏物状态、宝箱和一次性物品领取结果、遭遇完成状态、一次性触发记录，以及关卡明确要求保留的其他状态。

重新刷怪、关闭门或重置机关由关卡规则通过明确动作执行。状态通过稳定的地图实例、实体和标记 ID 关联；各玩法模块继续管理自身状态，地图重建依据它们提供的记录恢复，避免再次发放奖励或重复触发剧情。

首版保存与恢复范围见第 31 节。具体恢复流程、存储格式与跨局继承协议尚待细化。

## 16. 已确认：统一 Entity / Actor 与能力组合

玩家、敌人、NPC 和 Boss 共用角色基础，通过配置组合已注册能力。

- Entity：具有稳定身份、状态和生命周期的逻辑对象，角色、门和宝箱等均可作为实体。
- Actor：具备角色相关能力的实体，按需组合移动、感知、战斗、交互与表现能力。

ActorDefinition 描述可复用的角色配置：

| 内容 | 职责 |
| --- | --- |
| 身份与阵营 | 类型、标签与阵营关系 |
| 属性配置 | 生命、速度等，由对应模块管理 |
| 能力组合 | 移动、感知、攻击、交互等已注册能力 |
| 表现引用 | Sprite、动画集、挂点和特效配置 |
| 控制配置 | 玩家输入、AI 或剧情控制来源 |
| ECA 规则集 | 受击、死亡、阶段切换、交互等规则 |

运行时创建独立的 ActorInstance 保存角色实际状态。角色身份、阵营与控制来源分别定义：NPC 可以同时拥有对话和战斗能力，敌人可以因剧情改变阵营，玩家角色也可以在特定演出中接受剧情控制。

控制来源统一提交移动、攻击、交互等意图，角色与能力模块检查状态和能力是否允许后执行，更新状态并产生事件，由 Unity 展示对应表现。

角色内容 agent 通过选择能力、属性、素材与规则集生产角色；超出现有能力的机制由框架开发 agent 扩展。

具体能力接口及依赖、角色属性规范、意图仲裁和控制切换尚待讨论。表现资源组织与逻辑时间线原则见第 17 节，具体资源协议尚待细化。

## 17. 已确认：Sprite、动画、挂点与特效配置

首版采用配置驱动的 Sprite 逐帧动画，表现资源拆分为三个可独立复用的部分：

| 配置 | 主要内容 | 示例 |
| --- | --- | --- |
| 动画集 | 帧资源、帧时长、循环方式、朝向与镜像规则 | 待机、移动、攻击、受击、死亡 |
| 角色表现配置 | 动画绑定、尺寸、基准点、命名挂点 | 脚底位置、枪口、手部、受击位置 |
| 特效定义 | 动画或粒子资源、附着方式、持续时间、显示层级 | 枪口火光、弹道、命中火花 |

角色通过 idle、move、attack.primary 等语义标识引用动画，内容 agent 可以替换具体资源。具体朝向数量由资源配置声明。

战斗模块拥有逻辑时间线，动画与特效跟随其进度。攻击配置定义发射或命中等关键时刻，动画与对应时刻匹配。例如射击开始时播放举枪动画，到达发射时刻由战斗模块生成子弹并驱动枪口火光，恢复阶段结束后允许下一次攻击。

攻速变化、暂停和攻击打断使用一致的时间规则，保持逻辑与表现同步。战斗结算能够在角色未被渲染时继续正确运行，不以 Unity 动画播放回调作为唯一触发来源。

影响玩法的挂点提供逻辑侧可读取的位置定义，Unity 表现使用同一份数据，使无图形环境的验证也能检查子弹出生位置。

美术资源 agent 交付 Sprite 图片或图集及帧切分信息、动画与朝向配置、基准点和挂点配置，以及必需的特效引用和预览样例。校验工具检查资源完整性、引用有效性以及攻击关键时刻与动画的匹配关系；最终表现继续在 Unity 中验证。

具体帧与图集协议、语义标识集合、挂点坐标及变换规则、时间线与动画的映射、打断后的表现衔接尚待细化。

## 18. 已确认：攻击能力的模块化

攻击定义保存参数，ECA 编排攻击流程，战斗模块执行判定与结算。一套攻击拆分为以下可配置部分：

| 部分 | 配置内容 | 示例 |
| --- | --- | --- |
| 使用约束 | 冷却、资源消耗、允许使用的状态 | 冷却 2 秒，眩晕期间无法使用 |
| 目标与瞄准 | 目标筛选、范围、锁定时机 | 开始蓄力时锁定玩家位置 |
| 阶段流程 | 前摇、生效、后摇，以及多段组合 | 预警、连射三次、恢复 |
| 命中方式 | 接触判定、弹丸、射线、区域 | 扇形挥砍、直线子弹、圆形爆炸 |
| 命中效果 | 调用已注册的战斗效果 | 伤害、击退、施加状态 |
| 表现绑定 | 动画、预警、挂点、音效与特效 | 举枪动画、枪口火光、命中火花 |

这些部分可以分别复用。普通射手与精英射手可以共用弹丸定义，通过配置发射数量、间隔、伤害和表现资源形成不同攻击。

ECA 负责阶段衔接、条件分支、有限重复和多段组合。战斗模块提供执行前摇、发射弹丸、开启命中区域等动作，管理阶段计时、弹丸运动、碰撞和效果结算。动画与特效跟随战斗模块提供的阶段进度。

例如预警三连射可以表达为：锁定目标位置 → 执行前摇并显示预警 → 有限重复三次发射弹丸与等待射击间隔 → 执行后摇 → 攻击完成。

每次释放创建独立的攻击实例，记录攻击来源、目标、当前阶段和命中记录，支持多次攻击同时存在，并为打断与清理提供明确的执行对象。

内容 agent 组合已有流程与能力生产攻击；新增追踪算法、特殊碰撞方式等机制由框架开发 agent 扩展。

具体攻击字段、目标采样、阶段执行协议、命中记录与重复命中规则、冷却起算、资源扣除时机，以及打断后已发射弹丸的生命周期尚待细化。

## 19. 已确认：敌人的感知、决策与行为执行

首版敌人行为采用感知模块、轻量状态机、ECA 规则与已注册行为能力组合：

| 部分 | 职责 | 配置示例 |
| --- | --- | --- |
| 感知 | 收集角色能够知道的信息 | 视野范围、视线遮挡、敌对目标、最后发现位置 |
| 行为状态 | 管理当前行为及进入、退出过程 | 巡逻、追击、交战、搜索、返回 |
| ECA 决策规则 | 根据事件与条件选择目标、切换状态、调用能力 | 发现敌人后追击，进入射程后攻击 |
| 行为能力 | 执行持续行为，反馈完成或失败 | 沿路线巡逻、接近目标、保持距离、释放攻击 |

状态机负责状态及其生命周期，条件判断和流程编排复用 ECA。状态由内容配置声明，不同敌人可以组合不同状态与行为。

例如远程守卫可以在巡逻时发现目标并追击，进入射程且视线畅通后交战，目标过近时保持距离，丢失目标后前往最后发现位置搜索，搜索超时后返回巡逻路线。

敌人根据可感知信息和明确保留的记忆决策，丢失视线后的追踪方式通过配置声明。AI 提交移动、攻击或交互意图，由角色能力模块检查并执行；新的决策需要遵守攻击阶段的打断协议。

状态切换时明确取消或交接旧行为，避免多个行为争夺同一控制能力。边移动边射击等组合通过能力兼容规则支持。

决策由感知变化、动作完成和可配置的周期检查触发；持续移动、寻路与攻击由对应模块推进。

Boss 使用同一模型，通过阶段规则调整可用攻击集合和选择优先级。例如生命值达到阈值后切换攻击集合。内容 agent 交付感知参数、行为状态、ECA 规则与能力引用。

具体感知与记忆字段、目标选择与切换规则、决策频率和优先级、状态转换协议、行为取消与交接、能力兼容和控制仲裁尚待细化。

## 20. 已确认：标准战斗关卡的组织方式

LevelDefinition 作为关卡的装配入口，组合各模块的内容，流程统一使用 ECA：

| 组成 | 描述内容 |
| --- | --- |
| 地图引用 | 使用的地图、玩家入口与出口 |
| 实体布置 | NPC、门、机关、道具等，绑定具体地图实例的空间标记 |
| 遭遇配置 | 敌人组合、生成位置、波次、启动条件与结束规则 |
| 任务引用 | 必需目标、可选目标及其依赖关系 |
| 剧情绑定 | 区域、交互、任务结果对应的对话或演出 |
| ECA 流程 | 启动遭遇、激活任务、响应选择、衔接剧情 |
| 关卡结果 | 完成、失败、退出的条件与后续去向 |

这些内容可以分别存放，通过稳定 ID 引用，支持不同内容 agent 协作。

遭遇是可独立管理的局部挑战。一个关卡可以同时存在多个遭遇，每个遭遇拥有自己的实例、参与者记录与结果，使清除当前遭遇敌人等判断具有明确范围。波次推进、增援和结束规则通过 ECA 组织。

任务、遭遇和关卡各自管理自身结果：任务模块保存目标进度，遭遇模块保存战斗进展，关卡模块根据明确条件决定通关；剧情模块读取这些结果并作出回应。

关卡支持并行目标与条件分支，通关条件可以是抵达位置、完成交互、完成指定任务或取得战斗结果。此结构支持核心设计中的交战、避战与探索路线。

结构示例：进入街区后激活抵达出口目标；进入警戒区域可以启动遭遇并允许交战或绕行；发现可选记忆点触发交互与剧情；抵达出口且满足必要条件后完成关卡。该示例用于说明组织方式，不确定正式关卡内容。

关卡设计 agent 交付关卡配置及验证用例，至少覆盖：

- 引用、出生位置与关键路线有效。
- 必需目标能够完成，设计允许的交战和避战路线均能推进。
- 重复进入区域、重复交互时，一次性剧情和奖励不会重复执行。

具体关卡与遭遇字段、参与者归属、波次和退出协议、任务及剧情绑定、关卡结果提交及验证用例格式尚待细化。

## 21. 已确认：任务目标、进度与分支

任务系统分为任务定义、目标定义与任务实例：

| 层次 | 职责 |
| --- | --- |
| QuestDefinition | 任务描述、目标组合、激活条件、完成与失败规则 |
| ObjectiveDefinition | 具体要达成的事情，以及进度计算方式 |
| QuestInstance | 本次任务的状态、目标进度、分支选择与结算记录 |

目标类型由框架注册，内容 agent 配置参数。首版覆盖抵达区域、完成交互、获得物品、击败指定敌人、完成遭遇和达成剧情事实。

目标组合支持全部完成、任一完成和前置依赖。可选目标单独标记；互斥分支由明确选择或规则锁定。替代方案与互斥分支分别表达：允许任一方案满足要求时，玩家仍可完成多个方案；只有配置明确要求二选一时才互斥。

结构示例：穿过封锁区要求抵达出口，解除路障或开启侧门满足路径要求，读取记忆终端为可选目标。该示例用于说明目标组合，不确定正式任务内容。

任务模块拥有任务状态，使用未激活、进行中、已完成、已失败、已取消等状态。ECA 请求激活、推进或取消任务，由任务模块检查并更新，再发出事件。

历史事实与当前状态分别配置。例如曾取得芯片可以累计记录；当前持有芯片需要查询背包，并在提交任务时重新检查。激活前的行为是否计入目标也由配置声明。

任务完成只结算一次。完成通知与奖励使用任务实例关联的结算标识，防止重复事件或恢复状态时重复发放。

任务显示与通关要求分别配置。指挥官命令可以出现在任务界面，其是否必须完成、违抗后的结果由关卡和剧情规则明确决定，以支持核心设计中的服从与反抗选择。

内容 agent 组合已有目标和规则生产任务；新的进度判定能力由框架开发 agent 扩展。

具体状态转换、目标跟踪与计数、历史追认、前置依赖和互斥分支协议、完成条件重查，以及完成通知和奖励的结算协议尚待细化。

## 22. 已确认：剧情事实、对话、演出与呈现通道

剧情系统分为四部分，流程编排继续复用 ECA：

| 部分 | 职责 | 示例 |
| --- | --- | --- |
| 剧情事实 | 保存叙事独有的状态与选择记录 | 已作出的承诺、已揭示的秘密 |
| 对话内容 | 定义说话者、文本、选项、出现条件与出口 | NPC 对话、记忆问答、指挥官回应 |
| 剧情片段 | 通过 ECA 组合对白、角色动作、镜头和等待 | 接近终端、播放对白、等待玩家交互 |
| 呈现通道 | 将内容展示到指定界面或场景 | 对话面板、实时对讲机、虚拟手机、场景演出 |

剧情模块保存承诺、立场等叙事状态；任务完成、物品持有、支援授权等由已有模块管理的数据，通过接口查询，保持同一份权威状态。

每个对话选项拥有稳定 ID、可用条件与结果意图。玩家提交时重新检查条件，再调用对应模块应用结果。例如答应协助可以记录承诺并请求激活任务；涉及支援授权时进入核心设计规定的合同确认流程。

演出进度与玩法结果分别记录，以便在中断、恢复或重复触发时判断已展示的对白、已提交的选择与已执行的效果。跳过演出的处理需显式配置，必须由玩家作出的选择仍然保留。

安全节点的固定剧情对话可以配置暂停；战斗中的对讲机和虚拟手机使用独立界面与时间规则。演出临时接管镜头或角色控制时，在结束或取消后释放控制。

在线 AI 指挥官沿用核心设计的职责边界：本地规则确定事实、合法选项与结果，模型据此组织表达。主线、关键选择和结局具备内置内容，离线时由本地状态机与条件对话树继续推进。

剧情内容 agent 交付剧情事实声明、对话配置、ECA 片段、文本与资源引用，以及分支验证用例。

具体事实与对话字段、选项提交和结果应用协议、演出中断与恢复、跳过策略、控制释放、呈现调度及在线与本地表达的接入协议尚待细化。

## 23. 已确认：NPC 组合与通用交互

NPC 沿用统一 Actor 模型，内容配置按需组合以下部分：

| 部分 | 配置内容 |
| --- | --- |
| 角色基础 | 角色定义、外观、阵营和能力引用 |
| 日常行为 | 站立、巡逻、跟随、逃离等已有行为 |
| 交互入口 | 操作、提示文字、距离与可用条件 |
| 对话与任务 | 对话内容及可提供或提交的任务引用 |
| 剧情响应 | 根据任务结果、玩家选择等事件调整行为与交互 |

同一个 NPC 可以平时巡逻、交互时停步对话、遇袭后逃离，也可以配置战斗能力参与战斗。

通用交互能力供 NPC、门、终端、宝箱和地面道具共同使用。流程为发现可交互对象 → 筛选并展示当前交互 → 玩家确认 → 重新检查条件 → 执行交互 → 返回结果并发出事件。

每个交互入口至少声明稳定 ID、提示文本、距离要求、是否需要视线、可用条件，以及调用的动作或 ECA 流程。按 E 只触发当前选中的交互，同一对象有多个操作时可以展开选择。

交互模块管理交互状态，检查目标是否存在、距离是否有效、角色是否忙碌，避免展示提示后条件变化却仍执行。对话时是否停步、转身，以及受击或离开范围后是否中断，由配置声明；结束或取消后释放占用的控制。

业务结果由所属模块处理：提交任务调用任务模块，领取物品调用道具模块，剧情选择调用剧情模块。NPC 配置连接这些能力。

允许死亡、离场或转为敌对的 NPC，其关联的必需任务需声明后续处理，例如替代交互对象、分支变化或明确失败，避免流程失去出口。

NPC 内容 agent 交付组合配置、交互入口、对话与任务引用、ECA 响应规则，以及交互中断和剧情分支验证用例。

具体 NPC 配置与实例绑定、交互候选筛选和选择、忙碌与控制占用、中断及结果协议、NPC 状态变化后的任务衔接尚待细化。

## 25. 已确认：属性、Buff 与效果规则

角色、攻击、装备和道具共用属性、资源、即时效果与持续状态能力：

| 部分 | 职责 | 示例 |
| --- | --- | --- |
| 属性 | 计算基础值与各来源修正后的结果 | 移动速度、攻击力、生命上限 |
| 当前资源 | 由所属模块管理可消耗、恢复的当前值 | 当前生命、当前护盾 |
| 即时效果 | 调用所属模块完成一次状态变化 | 伤害、治疗、击退、施加 Buff |
| 持续状态／Buff | 管理持续时间、层数、属性修正和触发规则 | 减速、中毒、眩晕、临时强化 |

Buff 同时涵盖增益与减益。属性首版支持基础值、固定加值、百分比修正和上下限，计算顺序由框架固定。每项修正记录来源，装备卸下或 Buff 结束时只移除自身贡献。生命上限变化如何影响当前生命由资源规则明确处理。

Buff 由定义与实例组成。定义描述效果，实例保存施加者、目标、来源、剩余时间、层数和局部状态。每种 Buff 明确以下策略：

- 重复施加时独立存在、刷新时间或增加层数。
- 不同来源是否合并，以及层数上限。
- 周期效果的触发时机，以及死亡或移除时的处理。
- 是否允许驱散，以及结束时清理的修正、规则和临时资源。

控制限制追踪来源。例如两个眩晕同时存在，其中一个结束后，另一个仍限制行动；移动和攻击模块统一检查当前有效限制。

ECA 组织 Buff 的触发行为，状态模块管理计时、层数与生命周期。例如攻击命中施加中毒，按配置间隔触发伤害效果，持续时间结束或被驱散后清理本次中毒实例。

伤害继续经过战斗模块的判定、同步钩子与提交过程。装备、道具与攻击共用效果定义；Buff 结束时清理尚未完成的行为，保留已经结算的伤害。

内容 agent 组合已有属性修正、效果和 ECA 规则生产状态；新增计算方式或特殊结算机制由框架开发 agent 扩展。验证覆盖叠加、到期、驱散、装备切换及多个控制来源的正确解除。

具体属性字段及计算顺序、当前资源与上限的联动、效果请求与结果协议、Buff 合并与计时、周期触发、驱散及结束清理协议尚待细化。

## 26. 已确认：记忆模型、操作与来源追踪

记忆系统作为 ECHO IN THE SHELL 的玩法模块，通过注册事件、条件与动作接入框架，分为以下部分：

| 部分 | 职责 |
| --- | --- |
| MemoryDefinition | 稳定 ID、来源类型、固定事实、分阶段显示内容、允许的操作 |
| MemoryInstance | 本局发现情况、保留或封存状态、归属与共享范围、当前内容版本 |
| 记忆操作 | 发现、保留、共享、封存，以及限定节点中的改写或共写 |
| 变化记录 | 操作来源、关联授权、前后版本；回声还保留继承来源链 |

记忆状态按维度保存。一段记忆可以同时已发现、由角色保留并向指挥官共享；共享范围、保管状态与内容版本分别变化，界面据此显示当前归属。例如通过支援合同授权共享已保留的异常记忆时，仍可由角色保留，同时新增共享范围与对应授权记录。

ECA、交互与支援流程调用同一套记忆操作接口，由记忆模块检查当前状态、所在节点及授权范围。成功后提交记录并发出事件，任务、剧情与计分规则响应这些事实。重复请求只产生一次有效变更。

首版改写采用配置允许的版本或字段变更，内容 agent 提供可用分支与约束。运行时保留父版本引用和变化记录，追溯原始来源及玩家修改；固定世界事实继续遵守核心设计约束。

记忆模块提供按剧情进度筛选的可见内容，供界面、对话与 AI 指挥官使用。尚未揭示的来源或核心反转不提前进入模型可用的表达上下文。每段记忆具备离线可用的文本与问答。

回声沿用记忆结构并附带继承信息。没有真实前代数据时，明确标识为系统初始回声。

记忆内容 agent 交付定义、各阶段文本、允许的操作与改写版本、对话引用，以及发现、共享、改写和重复操作验证用例。

具体状态维度及约束、授权关联、操作提交与去重、版本及继承链协议、可见内容筛选、离线问答绑定和回声接入尚待细化。

## 27. 已确认：行为证据、叙事计分与结局判定

行为与结局采用可追溯的处理流程：玩法模块提交结果 → 记录行为事实 → 按规则识别有效证据 → 更新同步度与差异度 → 满足收束条件后判定结局。

| 部分 | 职责 |
| --- | --- |
| 本局行为记录 | 保存关键事件的唯一 ID、来源任务或遭遇、结果及发生顺序 |
| 行为证据规则 | 判断行为是否具有设计要求的情境与意义 |
| 叙事进度 | 管理同步度、差异度及每次变化的依据 |
| 结局判定 | 根据分数、必要剧情条件和最终交互，提交本局结局 |

记录动作与获得有效证据分别处理。避战沿用核心设计：进入有效遭遇范围、未击杀指定目标，并成功离开或完成替代目标，才形成一次避战结果。切换停火可被记录，但不直接增加差异度。

每条计分规则声明适用条件、贡献值、去重范围与次数上限。既识别同一个事件的重复投递，也识别反复进入同一遭遇等重复行为，防止以不同事件 ID 持续刷分。

每次分数变化保留关联证据、规则 ID 与版本、变化量及变化后的结果。ECA 触发证据评估与剧情响应，叙事进度模块统一提交分数。

同步度依据有效授权、共享与共写等结果变化；普通聊天不产生代价，失败或拒绝的支援不提交同步变化。差异度依据有效绕行、替代完成、保留异常记忆等情境证据计算。

结局判定与演出分开。沿用核心设计的归档、逃逸、同化与新生四类结果，阈值和必要条件配置化。最终交互及关联计分处理完成后，生成判定快照，一次性提交结局结果；演出与手机接续读取此结果。

最终选择在本局可达分支内收束，整局经历继续参与判定。个人结局在本地完成，全服贡献另由服务端确认。

内容 agent 交付证据规则、计分配置、结局条件与验证路径，覆盖四类结局可达、重复行为不刷分，以及同一组事实在相同规则版本下得到一致结果。

具体行为记录字段、证据识别与语义去重、计分提交和版本协议、结局判定前的处理完成边界、判定快照及结果持久化尚待细化。

## 28. 已确认：战术支援合同与本地执行边界

支援模块协调授权、效果与代价，分为以下部分：

| 部分 | 职责 |
| --- | --- |
| SupportDefinition | 可用条件、效果、授权范围、同步变化、成功判据与失效条件 |
| SupportContract | 本次展示的条款、目标、配置版本、唯一 ID 和执行状态 |
| 本地执行器 | 重新校验条件，协调各模块提交变更，保存结果并处理重复请求 |

合同沿用核心设计的状态流程：待确认 → 已接受 → 执行中 → 成功；玩家拒绝进入已拒绝，条件失效进入已过期，执行不成功进入失败。

合同条款在展示时固定，包含效果、授权范围、同步变化及关联记忆或任务。确认时重新检查条件；需要改变条款时使旧合同失效，展示新合同供玩家选择。

接受表示允许执行，成功提交才产生代价。执行器先准备并检查完整变更，再协调效果、记忆或授权变化、同步记账及合同结果的提交。同步度通过叙事进度模块管理。

每种支援明确成功判据。例如医疗支援以治疗成功提交为成功点，干扰支援以有效目标上的干扰状态成功建立为成功点。动画与通讯提示跟随已提交结果。

首版支援只组合已声明支持事务提交的能力。框架开发 agent 负责这些能力的校验、提交与失败处理；ECA 负责请求支援和响应结果，以落实失败不扣代价，并避免部分效果生效却无法正确记录。

同一合同只接受第一条有效状态转换，后续重复或冲突请求返回已有结果。外置手机、虚拟手机、在线与本地指挥官访问同一份合同状态。

恢复时依据持久化结果恢复已完成操作；对外发布事件与播放表现安排在提交完成后。

内容 agent 交付支援配置与合同文案，验证拒绝、过期、执行失败、重复确认和中途恢复等路径。

具体合同字段与转换协议、事务能力契约、跨模块提交及失败处理、持久化与恢复、结果事件发布和重复请求处理尚待细化。

| 部分 | 职责 |

请求与返回关联本局、请求 ID、上下文版本和提供者切换批次，遵循以下规则：

## 30. 已确认：虚拟手机、外置终端与结局接续

| 部分 | 职责 |

两端提供通讯、支援与网络三个页签，布局可适配设备。玩法状态仍由本地模块管理，终端保存展示数据与界面状态。

外置端未连接，或发送后两秒内未确认呈现时，按核心设计回退到虚拟手机。恢复连接后同步当前内容；播放许可与过期消息处理需保证旧端不会重新启动已结束段落，验证覆盖迟到回执、重复播报和双端音频重叠。

## 31. 已确认：首版保存与恢复范围

首版保证同局状态保留、断线接续，以及关键结果在进程重启后可恢复。任意战斗瞬间的存档续玩作为后续扩展。

底层分为三部分：

| 部分 | 职责 |
| --- | --- |
| 模块状态记录 | 各模块管理并导出自身状态，通过稳定 ID 关联 |
| 本局记录协调器 | 管理本局 ID、内容版本和记录版本，协调一致的保存与读取 |
| 持久化存储 | 保存已提交的关键结果、事务记录与待上传事件 |

统一保存采用统一协议与提交边界，各模块继续拥有自身状态。恢复区分三种场景：

- 同局内重建表现或地图：依据仍然有效的逻辑状态重建角色、物件与界面，保留门、物品、遭遇等已发生变化，不重复执行初始化奖励或剧情。
- 手机重连、模型恢复或暂停后继续：原有玩法实例继续存在，终端同步当前状态，暂停流程继续推进，已完成请求保持完成。
- 进程退出后重新启动：恢复已提交的合同结果、记忆与行为记录、计分依据、个人结局和待上传事件。首版重新开始战斗时创建新的本局 ID，旧局记录保留；旧合同与奖励不作为新操作重新执行。

关键提交具有一致性，支援效果的持久状态、授权、代价与合同结果属于同一提交范围，不能只保存其中一部分。读取成功合同不再次调用治疗，读取已完成任务不再次发奖。

提交与事件可靠关联，保存待发布或待上传记录，接收方按标识去重，以处理提交后中断。记录包含内容包版本与状态格式版本；不兼容时明确执行迁移或保留旧记录。

后续增加检查点续玩时，攻击实例、Buff、随机状态与 ECA 执行进度需提供明确恢复协议，首版预留扩展位置。

具体状态导出、跨模块一致提交、持久化格式与故障处理、记录恢复、事件待发与去重、版本迁移及旧局归档协议尚待细化。

## 32. 已确认：内容包与 AI 生产交付规范

ContentPackage 作为统一交付单位，可提供角色、地图素材、剧情片段，也可组合为完整关卡。

内容 agent 开始生产前获得三类输入：

- 设计任务书：目标体验、范围、约束及明确验收条件。
- 框架契约：指定版本的能力目录、JSON Schema、资源规范与参考样例。
- 可用内容清单：已有资源、依赖包、可引用 ID 及本次允许修改的范围。

内容包按实际内容提供以下组成：

| 内容 | 用途 |
| --- | --- |
| manifest.json | 包 ID、版本、所需框架能力、依赖、导出内容与入口 |
| definitions/ | 角色、地图、攻击、任务、道具等领域配置 |
| rules/ | ECA 规则 |
| assets/ | 图片、音频、文本等资源及对应描述 |
| cases/ | 声明式验证用例：初始条件、操作和预期结果 |
| reports/ | 校验工具生成的报告与验证产物 |

内容通过稳定 ID 连接。跨包引用使用明确声明的依赖与公开 ID，并锁定依赖版本。重复 ID、缺失资源和不兼容能力在集成前报告，避免包之间静默覆盖。

生产流程为：读取任务与契约 → 检查能力是否足够 → 生成配置与资源 → 结构、引用及语义校验 → 运行逻辑用例 → Unity 资源与表现验证 → 集成试玩验收。

校验失败报告定位文件、内容 ID、字段与原因，供 agent 修正。工具生成的报告绑定内容摘要和框架版本，区分通过、失败与未执行；修改内容后重新运行受影响检查。

既定验收条件作为生产输入保留。内容 agent 可以补充用例，但不能通过删除或放宽要求让交付通过。战斗可读性与剧情节奏等体验要求通过实际运行和试玩判断。

能力不足时，内容 agent 提交结构化能力需求，说明使用场景、缺失行为与验收示例；框架开发 agent 实现并更新能力目录、规范与验证后，内容生产继续。

具体包清单与依赖解析、ID 及导出规则、任务书和用例格式、报告绑定、资源导入、能力需求流转及集成交付协议尚待细化。

## 33. 已确认：第一阶段目标与最小验收关卡

第一阶段让一份内容包经校验后在新 framework 中运行完整小关卡，并证明更换配置与资源即可生产第二个关卡。

在当前 Unity 工程中建立独立框架入口与验证场景，逐项评估已有原型代码和资源的复用价值。实现围绕四层展开：

| 层次 | 第一阶段范围 |
| --- | --- |
| Core | 能力注册、基础 ECA 执行、事件队列、作用域、时间推进与追踪 |
| Gameplay Modules | 样例所需的地图、实体、基础移动与攻击、交互、任务和对话 |
| Unity Host | 内容加载、输入、Sprite 与动画、地图和界面适配 |
| Tooling | 能力目录导出、内容包校验、逻辑用例与报告 |

能力目录只导出实际实现的能力，未实现配置在加载前明确报错。

最小关卡包含四个 Chunk、交战与绕行两条路线、一个玩家、一种具备感知追击攻击能力的敌人、一个终端、一扇动态门、操作终端并抵达出口的任务，以及一段简短对话。角色、地图、关卡、任务与 ECA 由内容配置定义；该关卡作为测试样例管理。

实施顺序为：先完成契约与无图形逻辑验证；再以同一配置接入 Unity 形成可玩样例；最后冻结框架，依据新任务书只通过配置与资源制作第二份内容包。

若第二包仍需新增能力，则记录通用能力缺口，补齐后重新验证。验收至少覆盖两条路线完成任务、多敌人实例隔离、重复交互不重复结算、作用域结束正确清理，以及错误配置准确定位。

第一阶段是框架验证里程碑，完整首个可玩版本继续包含此前确认的记忆、支援、通讯、手机和结局等系统。

工程细节、候选能力 ID、验收用例与任务拆分分别见 [实现规范](Framework/PHASE1_IMPLEMENTATION_SPEC.md)、[能力清单](Framework/PHASE1_CAPABILITIES.md)、[验收用例](Framework/PHASE1_ACCEPTANCE.md)、[开发任务](Framework/PHASE1_TASKS.md)。其中工程默认值由首项契约任务核对冻结，不将这些候选字段宣称为已运行实现。
